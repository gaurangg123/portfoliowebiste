# DataForge — Engineering Intelligence

The portfolio of **Gaurang Ashava**, GET – Data and AI Engineer at Tata Technologies.

- **Live:** https://gaurangg123.github.io/portfoliowebiste/
- **What it covers:** the engineering domains I work across, the enterprise applications and experiments I've built, my experience and education.
- **Pages:**
  - the homepage, an editorial journey in nine chapters;
  - five case studies at `work/<slug>/`;
  - **Query the Engineer** at [`query-engineer/`](https://gaurangg123.github.io/portfoliowebiste/query-engineer/), a local portfolio assistant.
- **Interactive pieces:**
  - a right-side navigation rail;
  - a project gallery in three labelled groups;
  - a reference data architecture;
  - the Query the Engineer assistant;
  - a light/dark theme.

It is a static site: Node generates the HTML from `src/`, and GitHub Pages serves the files as they are. There is no runtime framework and no runtime dependency. Every page reads fully without JavaScript; scripts only add behaviour.

## Stack

| Layer | Choice |
| --- | --- |
| Pages | Static HTML generated by `tools/build.js` (Node 20+, no dependencies) |
| Styles | Hand-written CSS with design tokens (`src/styles/tokens.css`), bundled into `assets/css/dataforge.css` |
| Behaviour | Vanilla JavaScript modules (JSDoc-typed, `// @ts-check`), bundled into `assets/js/dataforge.js` |
| Hero visual | A custom 3D lattice on `<canvas>` (`src/scripts/hero-lattice.js`): no 3D library |
| Fonts | Space Grotesk, Inter, JetBrains Mono, self-hosted WOFF2 (SIL OFL) |
| Icons | Inline SVG in the style of Lucide |
| Quality | ESLint 10, TypeScript `--noEmit` (strict, `checkJs`), html-validate, `node:test`, Playwright, axe-core, Lighthouse |
| Hosting | GitHub Pages, branch deploy from `main` (root), `.nojekyll` |

Why no React or Vite? The brief asked to keep the existing stack where practical. Static HTML gives the best performance and SEO, works without JavaScript, and needs no Pages build pipeline. See `docs/audit-and-plan.md`.

## Local setup

```bash
npm install            # dev tools only: ESLint, TypeScript, Playwright, html-validate, axe
npm run dev            # build, then serve at http://127.0.0.1:4173/portfoliowebiste/ and rebuild on save
```

The preview behaves like GitHub Pages:

- the site is served under `/portfoliowebiste/`;
- folders serve their `index.html`;
- missing paths get `404.html` with status 404;
- text is gzipped.

## Deploying

GitHub Pages publishes the root of `main`, so the generated files are committed.

1. `npm run check`. Everything must pass.
2. Commit the sources and the generated output (`index.html`, `work/`, `404.html`, `assets/css`, `assets/js`, `sitemap.xml`).
3. Push a branch, open a pull request into `main`, and merge it. The **pages build and deployment** workflow publishes it within a minute or two.

The site lives under the `/portfoliowebiste/` subpath:

- Pages link relatively (`assets/…`, `work/<slug>/`).
- `404.html` uses absolute `/portfoliowebiste/` URLs because it is served at any depth.
- The canonical URL, sitemap and Open Graph tags use `https://gaurangg123.github.io/portfoliowebiste/`.

## Updating content

All content is in `src/data/`. Edit it there, then run `npm run build`.

**A project:** add or edit an entry in `src/data/projects.js`.

- Company projects get a case study at `work/<slug>/`.
- They need a walkthrough entry in `assets/walkthroughs/demos.js`, because titles come from there.
- They also need a cover:
  1. Add a drawing in `tools/art/covers.js`.
  2. Run `npm run assets`.
- `categories` drives the filters.
- Leave `status`, `tech`, `repo` and `demo` as `null` until they are confirmed. The page then shows a clearly marked placeholder.

**Experience:** edit `src/data/experience.js`.

- `achievements` are always shown.
- `more` sits behind "More responsibilities".

**Education and certifications:** edit `src/data/education.js`. A new certification appears on the homepage.

**Disciplines, workflow and architecture:** edit `src/data/domains.js`, `src/data/workflow.js` and `src/data/architecture.js`.

- All three render through one component, the stepper (`src/components/stepper.js`): a horizontal journey (workflow, architecture) or a list beside a stage (disciplines) on wide screens, and a vertical timeline on small screens and without JavaScript.
- Discipline tool lists are fixed by a unit test; change them there too.
- Each workflow stage's example must link a documented case study. The workflow describes an approach, not a claim that every activity happened on every project.
- The architecture `uses` entries link stages to documented work; it is a reference model, not one project's architecture.
- Illustrations for stages are inline SVG in `src/components/scenes.js` and follow the theme.

**Links:** edit `src/data/site.js`. The résumé must stay the Google Drive *viewing* URL, unchanged. A unit test checks this.

**Sections and navigation:**
- The rail and the small-screen menu list `sections` from `src/data/site.js` (id, label, icon). `tools/build.js` assembles the homepage in the same order.
- On screens 1024px and wider, the rail is fixed to the right edge. `.container` keeps clear of it through `--rail-space`, so content never runs underneath.

**Query the Engineer** (`/query-engineer/`) is a transparent, local assistant, not an AI chatbot. It has no model, no API and no network calls.
- **Where answers come from:** `src/scripts/query-engine.js` matches a question against `src/data/query.js`, which the build assembles from the same data as the pages.
- **Adding knowledge:** add it to the data. Add aliases for a project or organisation in `src/data/query.js`.
- **Tests:** `qa/unit/query.test.js` checks that answers stay on topic, link only to places the data names, and decline what isn't documented.
- **Without JavaScript:** the page shows the engine's answers to the eight suggested questions, pre-rendered at build time.
- **Old links:** the old terminal's `#terminal` address on the homepage now opens this page.

**Theme:** colours are tokens in `src/styles/tokens.css`, with a `:root[data-theme="light"]` block for the light theme. Dark is the default; the visitor's choice is stored in `localStorage` (`df-theme`) and applied before the first paint. `qa/unit/contrast.test.js` checks text contrast for both themes from the tokens.

**Content rules** are enforced by `qa/unit/content.test.js`. There must be no invented:

- metrics or percentages;
- production dates;
- statuses;
- public repositories.

## Accessibility and motion

- Semantic landmarks, one `h1` per page, a skip link, and visible focus everywhere.
- The navigation rail is a list of links with names that appear on hover and focus. The current section is marked with `aria-current`.
- The small-screen menu is a modal: Escape closes it, focus stays inside, and the page behind is inert.
- The architecture is a single-open accordion: each stage is a heading with a button (`aria-expanded`), and arrow keys, Home and End move between stages.
- The Query page's conversation is a polite live region. Typed text is only ever set as text, never parsed as HTML.
- The project gallery's filters are toggle buttons, and the result count is announced.
- The wordmark, the floating button and the footer link return to the top without adding `#top` to the address; an old `#top` address is cleaned on load. Section and case-study fragments are kept, and Back returns to the section you left.
- `prefers-reduced-motion` is honoured: still lattice, instant scrolling, no reveals, no loops.
- The hero's **Pause motion** control stops every continuous animation and is remembered.
- Continuous animations run only while on screen. The lattice pauses in background tabs and uses fewer nodes on low-power devices.
- Walkthroughs never autoplay, and the site plays no audio.
