# DataForge — Engineering Intelligence

The portfolio of **Gaurang Ashava**, GET – Data and AI Engineer at Tata Technologies.

- **Live:** https://gaurangg123.github.io/portfoliowebiste/
- **What it covers:** the engineering domains I work across, the enterprise applications and experiments I've built, my experience and education.
- **Interactive pieces:** a reference data architecture and a working (simulated) terminal.

It is a static site: Node generates the HTML from `src/`, and GitHub Pages serves the files as they are. There is no runtime framework and no runtime dependency. Every page reads fully without JavaScript; scripts only add behaviour.

## Stack

| Layer | Choice |
| --- | --- |
| Pages | Static HTML generated by `tools/build.js` (Node 20+, no dependencies) |
| Styles | Hand-written CSS with design tokens (`src/styles/tokens.css`), bundled into `assets/css/dataforge.css` |
| Behaviour | Vanilla JavaScript modules (JSDoc-typed, `// @ts-check`), bundled into `assets/js/dataforge.js` |
| Hero visual | A custom 3D lattice on `<canvas>` (`src/scripts/hero-lattice.js`): no 3D library |
| Fonts | Space Grotesk, Inter, JetBrains Mono, self-hosted WOFF2 (SIL OFL) |
| Icons | Inline SVG in the style of Lucide |
| Quality | ESLint 10, TypeScript `--noEmit` (strict, `checkJs`), html-validate, `node:test`, Playwright, axe-core, Lighthouse |
| Hosting | GitHub Pages, branch deploy from `main` (root), `.nojekyll` |

Why no React or Vite? The brief asked to keep the existing stack where practical. Static HTML gives the best performance and SEO, works without JavaScript, and needs no Pages build pipeline. See `docs/audit-and-plan.md`.

## Local setup

```bash
npm install            # dev tools only: ESLint, TypeScript, Playwright, html-validate, axe
npm run dev            # build, then serve at http://127.0.0.1:4173/portfoliowebiste/ and rebuild on save
```

The preview behaves like GitHub Pages:

- the site is served under `/portfoliowebiste/`;
- folders serve their `index.html`;
- missing paths get `404.html` with status 404;
- text is gzipped.

## Commands

| Command | What it does |
| --- | --- |
| `npm run build` | Generates every page, the CSS and JS bundles, `sitemap.xml` and `robots.txt` |
| `npm run dev` | Build, serve and rebuild when `src/` changes |
| `npm run preview` | Serve the current build |
| `npm run lint` | ESLint over the sources and tools |
| `npm run typecheck` | TypeScript type-check of the browser scripts and tests |
| `npm run validate:html` | html-validate on every generated page |
| `npm run test:unit` | Terminal logic and content guardrails (`qa/unit/`) |
| `npm run test:e2e` | Playwright functional, accessibility and responsive tests (`qa/playwright/`) |
| `npm run check` | All of the above, in order |
| `npm run assets` | Re-render the artwork and rebuild `deliverables/dataforge-assets.zip` |
| `node qa/capture-screenshots.js <dir> [--jpg] [--full]` | Visual QA screenshots at the nine QA viewports, plus layout checks |

## Deploying

GitHub Pages publishes the root of `main`, so the generated files are committed.

1. `npm run check`. Everything must pass.
2. Commit the sources and the generated output (`index.html`, `work/`, `404.html`, `assets/css`, `assets/js`, `sitemap.xml`).
3. Push a branch, open a pull request into `main`, and merge it. The **pages build and deployment** workflow publishes it within a minute or two.

The site lives under the `/portfoliowebiste/` subpath:

- Pages link relatively (`assets/…`, `work/<slug>/`).
- `404.html` uses absolute `/portfoliowebiste/` URLs because it is served at any depth.
- The canonical URL, sitemap and Open Graph tags use `https://gaurangg123.github.io/portfoliowebiste/`.

## Updating content

All content is in `src/data/`. Edit it there, then run `npm run build`.

**A project:** add or edit an entry in `src/data/projects.js`.

- Company projects get a case study at `work/<slug>/`.
- They need a walkthrough entry in `assets/walkthroughs/demos.js`, because titles come from there.
- They also need a cover:
  1. Add a drawing in `tools/art/covers.js`.
  2. Run `npm run assets`.
- `categories` drives the filters.
- Leave `status`, `tech`, `repo` and `demo` as `null` until they are confirmed. The page then shows a clearly marked placeholder.

**Experience:** edit `src/data/experience.js`.

- `achievements` are always shown.
- `more` sits behind "More responsibilities".

**Education and certifications:** edit `src/data/education.js`. A new certification appears on the homepage and in the terminal.

**Domains and the architecture diagram:** edit `src/data/domains.js` and `src/data/architecture.js`. The `uses` entries link stages to documented work.

**Links:** edit `src/data/site.js`. The résumé must stay the Google Drive *viewing* URL, unchanged. A unit test checks this.

**The terminal:** it answers from the same data, through `src/data/terminal.js`. To add a command:

1. Add it in `src/scripts/terminal-core.js`.
2. Add a test in `qa/unit/terminal.test.js`.

**Content rules** are enforced by `qa/unit/content.test.js`. There must be no invented:

- metrics or percentages;
- production dates;
- statuses;
- public repositories.

## Accessibility and motion

- Semantic landmarks, one `h1` per page, a skip link, and visible focus everywhere.
- The architecture diagram follows the ARIA tabs pattern.
- The terminal output is a live log; typed text is never parsed as HTML.
- `prefers-reduced-motion` is honoured: still lattice, no reveals, no loops.
- The hero's **Pause motion** control stops every continuous animation and is remembered.
- Continuous animations run only while on screen. The lattice pauses in background tabs and uses fewer nodes on low-power devices.
- Walkthroughs never autoplay. Papercut plays only when Play is pressed, and its file isn't requested before that.
